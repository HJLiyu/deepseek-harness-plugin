---
name: collaborate
description: Start persistent Codex × Harness project groups with shared chat, reusable contexts and visible peer collaboration, or manage legacy bounded goals.
---

For group chat, use `group_page` and open its local URL with `open_in_codex`; do not publish the URL's access token. `create_group` binds one Git project, creates two dedicated contexts and independent worktrees, and requires the connected Harness companion. Choose each model/effort once; never silently switch models. `group_input` queues a human demand with stable inputId; supplements and urgent inputs preempt at safe boundaries. Never submit peer replies as human input or infer approval from sender labels. `group_status`, `group_messages`, `list_groups` and `group_control` inspect/control the persistent group. Both peers read each initial demand, then choose division/integrator; default 3 discussion rounds. Do not manually relay their dialogue.

Planning `owner` names work executors only; reviewers are separate. At the round cap, routine division differences use the agreed integrator's proposal (otherwise a per-demand rotating proposer) with independent review and without extra model negotiation. This scheduling choice is not substantive consensus or human authorization. For a real requirement, permission or product choice, return `decision:{question,options}` with concrete alternatives; never hide that choice in a routine owner disagreement. Integrations use coordinator-captured per-request work deltas, not all accumulated worktree history; verification-only work can have an empty file scope. Concurrent main edits and stale member bases remain protected.

When the human asks to finish all original requirements, preserve the full goal rather than just the latest acceptance subtask. A `goalRequirements` list may seed immutable ids/titles. The coordinator adds an independent read-only `goalAudit` after each integration; return the complete `completionChecklist` with evidence and pending/blocked steps. Pending original work automatically continues in batches using the same contexts. An empty code delta does not prove the whole goal complete. Report only the verified stage until all original items pass; do not invent new goals or treat the ledger as permission approval.

Bound native chats require the trusted UserPromptSubmit hook / Harness pre-step adapter to route input before execution. Do not claim native routing from installation alone. Explicitly distinguish observed host evidence from unverified capabilities. Native plain text uses automatic routing: supplement the unfinished request, or create a demand while idle. Use “新需求：” / `/new` to explicitly queue independent work, “补充：” / “纠正：” to steer current work and “紧急：” to preempt. Group source labels do not authorize escalation. Host approval prompts remain human-owned. Unknown token usage stays unknown; unsupported strict hard limits block model admission. Preserve originals and checkpoints, and recover uncertain deliveries before considering retries.

Pin each group to its original Harness profile. Never route a desktop v4 log into a v3 CLI or replace contexts to hide recovery failures. Native controller messages are correlated through exact pending delivery bodies and host request IDs; a user role alone does not prove human authorship. `settle` reads an existing checkpoint while paused without starting another model turn. A legacy coordinator without the authenticated update protocol requires a user-controlled restart; never kill an assumed PID or start a competing executor. New worktrees include a private snapshot of current source; preserve the user's main branch/index and integrate only peer changes after that baseline.

For a legacy single bounded goal, use `start_collaboration` with a concrete objective, acceptance criteria, Git workspace, DeepSeek model and finite round cap. The plugin starts an independent Codex chat; it sends each Harness reply as a clearly identified user-role message to that chat.

`start_collaboration` creates or reuses the native `Codex × Harness` sidebar section, moves the thread into it and verifies persistence. Inspect its `sidebar` / `sidebarError` result; use `organize_sidebar` for repair. Report the goal ID and thread to the user. Do not claim sidebar success from source inspection alone.

Use `collaboration_status` and `collaboration_events` to inspect progress. To pause or stop, use the corresponding tools. A human message in the collaboration chat pauses automatic turns. Resume only after incorporating that message into the objective. If Harness requests extra permission, show the exact request and its request ID. The human must send the exact approval or rejection phrase containing both goal ID and request ID shown by the plugin. Pass that same request ID to `decide_harness_permission`; MCP and CLI both verify the fresh native chat message. Harness itself cannot approve its own escalation.

Use `list_collaborations` to recover saved goal IDs and filter statuses without loading message bodies. Use `collaboration_transcript` for bounded dialogue pages with stable message IDs, replyTo, source, stop reason and legacy Parley aliases; keep `collaboration_events` for tool diagnostics. Transcript history covers retained rotated logs only. Missing historical thread identities remain null. Informational authorization fields do not authorize operations; continue to use native human approval checks.

Each goal uses a separate Git worktree for Harness changes. Codex reviews and verifies changes before integrating them into the main project. Preserve the native chat, event files, and worktree on failures for inspection. Never claim full completion from a round limit alone.

When the desktop owns the thread writer, the coordinator uses the desktop app tools bridge to dispatch the identified Harness input and correlate its reply. The native record uses an external delegation item for this route. Preserve that identity; do not present it as a human approval. The coordinator reuses an existing matching dispatch on retry.

Use `adopt_codex_thread` to change the canonical native chat; never edit goal.json to switch threads. Adoption requires a paused worker checkpoint with no pending approval or undelivered Harness message. It verifies the replacement chat and sidebar and commits the thread, seen user turns and sidebar together. Permission requests and decisions are bound to their originating native thread; a decision from a replacement chat requires a fresh request. Status only treats sidebar verification as current when its saved thread binding matches the goal.

For a new project, create_group accepts createProject:true, projectName and absolute projectsRoot instead of workspacePath. This creates a new exclusive directory, Git repository and empty initial main commit before normal group setup. Never use this mode for an existing folder; use workspacePath instead. Preview in the shared form performs no writes.

For companion updates, validate the staged package closure and run `companion-update desktop` (or the pinned web profile) from the installed CLI with the actual HARNESS_PLUGIN_DATA. This gates new admissions, waits for current native operations and approvals, installs dependencies before the entry module, and requests the host's normal HMR through the owned config revision. Verify applied=true plus the native module-build receipt; file hashes alone do not prove a loaded update. Prefer this automatic path over asking the human to restart. If the host lacks HMR or the update is deferred, report the exact limitation and preserve pending work; do not force a process restart, bypass approvals or replace contexts. A stale adapter generation must never overwrite the latest instance, including after coordinator restart.

Never run scripts/install-local.mjs from a group member's own native turn. Use an independent maintenance context after native work and approvals settle; same-version updates reuse the enabled registration rather than invoking plugin/add again. prepare-update gates admissions and waits for existing work; it must not interrupt native turns. An unchanged verified module/configuration skips HMR. If an old planning dispatch lacks a native receipt, absence alone is not non-admission proof: only a superseded read-only dispatch may be quarantined after complete terminal native history plus authoritative desktop-idle evidence. Unknown work/integration remains protected. Record native turn/start receipts immediately, bound to thread and original prompt hash.
